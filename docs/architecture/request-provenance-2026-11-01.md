## 官方编码核对与多模型适配边界

2026-11-01 后续只读研究确认，DeepSeek-V4.1-Flash 官方仓库同时公开了 [inference](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/tree/main/inference)、[Python 编码器](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/encoding/encoding.py) 和 [Jinja 模板](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/chat_template.jinja)。Python 的 `render_reasoning_effort` 将 low/high/max 映射为 50/75/100，并在思考模式首条输入前写入 `Reasoning Effort` 明文；`render_message` 同时写入 system 边界标记。

因此实际链路是：用户与节点配置 → API 请求字段 → 服务端消息编码 → 模型输入。既有记录覆盖客户端请求与响应，没有覆盖托管服务最终编码后的全部输入。模型在推理中考虑有效运行控制，在机制上符合指令遵循；不能只靠控制词命中就判为不合格。公开编码没有 `verbosity` 字段，故尚不能把 5 换算成某个已证实的 effort。

源码、模板与服务协议还需分别版本化：本次读取的 Python 编码器接受 low/high/max 和整数；Jinja 模板另外接受 medium 并映射 62；官方 API 的[模型能力元数据](https://api-docs.deepseek.com/api/list-models/)则声明服务支持的档位与默认值。不能把某一个入口的取值直接外推到所有同名模型部署。

对后续适配采用以下边界，当前只完成审计和文档，不声称已增加新的适配功能：

- 核心保存用户选择的思考模式、原生档位、输出容量与可选风格，能力未知时保留未知；不能把“未声明”自动当成不支持或通过。
- 服务适配按提供方、模型版本、端点及协议选择字段，优先消费模型列表/能力接口；人工设置与实测证据保持独立。相同档位名称不保证相同计算投入。
- 托管 API 使用上游支持的参数，由上游编码；本地部署固定官方模板/编码器版本。不要在请求消息中再拼一份供应商的 effort 前缀，造成重复控制。
- 原生推理、工具回传、system 更新、流式事件与 token 用量都属于协议适配；Chat 兼容只保证部分接口形状，不保证这些语义相同。
- 训练投影保留我们明确提供的控制条件及其版本、原生推理和答案。不反向猜造未公开的服务端指令，也不把未知配置当作用户提出的事实。
- 上游易变的 DSH/Codex 插件继续独立维护；模型差异在 models 基础设施适配，不能散落到工作流、审核与导出规则中。

本次没有增加模型调用、改动原始请求/响应或调整产品质量校验；只修正诊断解释。文档和派生报告更新不运行全仓业务回归。
